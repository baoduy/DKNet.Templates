# DDD Implementation Guide

How to add one vertical-slice feature to a solution generated by `dotnet new dknet-minimal`,
end to end — domain entity, EF Core mapping, domain event, application action, endpoint,
and its tests. Every step below is grounded in the shipped `CustomerProfiles` slice; use it
as your copy-paste source. `LoyaltyMemberships` is a second, independent example of the same
shape if you want a cross-check.

> Path of truth: `src/ApiEndpoints/` (inner projects are prefixed `Minimal.*` in this repo;
> a generated solution renames them to `<YourApp>.*`).

## 1. Layer map

```
Minimal.Api          entry point, endpoints, auth, OpenAPI
  ↓
Minimal.AppServices   CQRS actions: request + validator + handler, DTOs, event handlers
  ↓
Minimal.Domains       entities, aggregate roots
  ↑
Minimal.Infra         EF Core mapping, seed data, repositories, event publisher, message bus
Minimal.Share         constants/options read by every layer
Minimal.AppHost       Aspire orchestration only (Redis + PostgreSQL + Api project)
```

No layer skips another. `Api` never references `Domains`/`Infra` directly — it dispatches
through `IMessageBus` (SlimMessageBus) to an `AppServices` handler.

## 2. Domain entity — `Minimal.Domains/Features/<Feature>/Entities/`

Reference: `Minimal.Domains/Features/Profiles/Entities/CustomerProfile.cs`

```csharp
public class CustomerProfile : AggregateRoot
{
    public CustomerProfile(string name, string membershipNo, string email, string phone, string byUser)
        : this(Guid.Empty, name, membershipNo, email, phone, byUser) { ... }

    public string Email { get; private set; }
    public string MembershipNo { get; private set; }
    public string Name { get; private set; }
    public string? Phone { get; private set; }

    public void Update(string? avatar, string? name, string? phoneNumber, DateTime? birthday, string userId)
    {
        // mutate private-set properties; null/empty means "leave unchanged" for name/phone
        SetUpdatedBy(userId);
    }
}
```

Rules that matter:

- `AggregateRoot` → `DomainEntity` → `AuditedEntity<Guid>` (from `DKNet.EfCore.Abstractions`) supplies
  `Id`, `CreatedBy`, `CreatedOn`, `UpdatedBy`, `UpdatedOn` — don't redeclare them.
- Every property setter is `private`. All mutation goes through entity methods (`Update(...)`)
  — never expose a public setter and never mutate from a handler.
  `Minimal.App.Tests/Architecture/RecordArchitectureTests.cs` and the `InfraTests`/`AppServiceTests`
  NetArchTest suite enforce shape rules like this; a public setter or a non-`sealed`/non-`internal`
  handler fails the architecture test suite, not just review.
- There is no soft-delete flag and no status/workflow field unless you add one — `CustomerProfile`
  only carries the properties it actually needs. Don't copy a `Status`/`IsDeleted` pattern from
  documentation without checking the entity source first.
- Folder name and feature name don't have to match: the entity lives under `Features/Profiles/`
  (singular) while the application slice below is `CustomerProfiles/V1/` (plural). Pick whichever
  reads better for your feature; the two are independent.

## 3. EF Core mapping — `Minimal.Infra/Features/<Feature>/Mappers/`

Reference: `Minimal.Infra/Features/Profiles/Mappers/CustomerProfileConfigs.cs`

```csharp
internal sealed class CustomerProfileConfigs : DefaultEntityTypeConfiguration<CustomerProfile>
{
    public override void Configure(EntityTypeBuilder<CustomerProfile> builder)
    {
        base.Configure(builder);
        builder.HasIndex(p => p.Email).IsUnique();
        builder.Property(p => p.Email).HasMaxLength(150).IsRequired();
        builder.ToTable("CustomerProfiles", DomainSchemas.Profile);
    }
}
```

- No manual `DbSet` and no manual `modelBuilder.ApplyConfiguration(...)` call anywhere — every
  `IEntityTypeConfiguration<T>` under the assembly is picked up automatically by
  `UseAutoConfigModel` (wired in `Minimal.Infra/Extensions/InfraSetup.cs`, `AddInfraServices`).
  Class must stay `internal sealed` (architecture tests check this) so it's only ever reached
  through the scan, never referenced directly.
- Give every `string` property an explicit `HasMaxLength` — an unconstrained string fails
  `InfraTests` and, on PostgreSQL, would otherwise map to unbounded `text`.
- Table/schema: `builder.ToTable(name, DomainSchemas.<Feature>)`. Add the schema to
  `Minimal.Domains/Share/DomainSchemas.cs` if your feature needs a new one.
- Optional seed data: drop an `IDataSeedingConfiguration<T>` next to the mapper, under
  `StaticData/` (see `Minimal.Infra/Features/Profiles/StaticData/CustomerProfileStaticData.cs`).
  It's discovered the same way, via `UseAutoDataSeeding`.
- After adding or changing a mapper, generate the migration from `src/ApiEndpoints/`:
  `./add-migration.sh <Name>` (wraps `dotnet ef migrations add -c CoreDbContext -p Minimal.Infra/Minimal.Infra.csproj`).

## 4. Application action — `Minimal.AppServices/<Feature>/V1/Actions/`

Reference: `Minimal.AppServices/CustomerProfiles/V1/Actions/Create.cs`

Each action file holds three things, in this order:

1. **Request** — implements `Fluents.Requests.IWitResponse<TDto>` (or `INoResponse` for
   delete-style commands with no return value). Package: `DKNet.SlimBus.Extensions`.
   - `[MapsFrom(typeof(Entity))]` on the request class registers a Mapster mapping between the
     entity and the request (see §6).
   - `[FromClaim(ClaimTypes.Name)]` on `ByUser` auto-populates the acting user from the bearer
     token — the endpoint pipeline overwrites any caller-supplied value, so it can never be
     spoofed in the request body.
2. **Validator** — `internal sealed class XCommandValidator : AbstractValidator<XRequest>`
   (FluentValidation). Runs automatically because every endpoint group calls
   `AddFluentValidationAutoValidation()` — you never call `Validate()` yourself.
3. **Handler** — `internal sealed class XCommandHandler(...) : Fluents.Requests.IHandler<XRequest, TDto>`,
   constructor-injecting whatever it needs (`IRepositorySpec`, `IMapper`, feature-specific services).
   `OnHandle` does the real work:
   - Query via a `Specification<TEntity>` for duplicate/uniqueness checks (see §5).
   - Map the request onto a new/loaded entity (`mapper.Map<TEntity>(request)`), then mutate it
     through entity methods only.
   - `repository.AddAsync(entity, ct)` / `repository.Delete(entity)` — no `SaveChanges` inside the
     handler in the create path shown here; the DKNet SlimBus pipeline calls it after the handler
     returns.
   - Raise domain events with `entity.AddEvent(new SomethingHappened(...))` — don't call the
     message bus directly from a handler.
   - Return `mapper.ResultOf<TDto>(entity)` (see §7) rather than `Result.Ok(mapper.Map<TDto>(entity))`
     when the DTO needs a value only available after `SaveChanges` (e.g. a DB-generated `Id`).

Handler and validator classes must be `internal sealed` — same architecture-test rule as the
EF config.

## 5. Query specs — `Minimal.AppServices/<Feature>/V1/Specs/`

Reference: `Minimal.AppServices/CustomerProfiles/V1/Specs/SpecGetCustomerProfile.cs`

```csharp
internal sealed class SpecGetCustomerProfile : Specification<CustomerProfile>
{
    public SpecGetCustomerProfile(Guid? byId = null, string? byEmail = null)
    {
        var predicate = CreatePredicate();
        if (byId is not null) predicate = predicate.And(a => a.Id == byId);
        if (!string.IsNullOrEmpty(byEmail)) predicate = predicate.And(a => a.Email == byEmail);
        WithFilter(predicate);
    }
}
```

One spec class per query shape, built from `DKNet.EfCore.Specifications`. Handlers ask
`IRepositorySpec` for `AnyAsync(spec, ...)` / `FirstOrDefaultAsync(spec, ...)` — never write a raw
LINQ query against the `DbContext` from a handler.

## 6. DTO and Mapster wiring — `Minimal.AppServices/<Feature>/V1/<Feature>Dto.cs`

Reference: `Minimal.AppServices/CustomerProfiles/V1/CustomerProfileDto.cs`

```csharp
[GenerateDto(typeof(CustomerProfile), Exclude = [])]
[MapsFrom(typeof(CustomerProfile))]
public sealed partial record CustomerProfileDto;
```

- `[GenerateDto]` (source generator, `DKNet.EfCore.DtoGenerator`) emits the DTO's properties from
  the entity at compile time — you never hand-write the property list.
- `[MapsFrom]`/`[GenerateDto]` on every decorated type are what `AppSetup.cs`'s
  `TypeAdapterConfig.GlobalSettings.ScanMaps()` reflects over to register every entity↔request and
  entity↔DTO Mapster mapping in one pass at startup. Adding the attribute is the *entire*
  registration step — there is no per-feature `TypeAdapterConfig` file to touch.

## 7. Lazy mapping — `Minimal.AppServices/Extensions/LazyMapper/`

`mapper.ResultOf<TDto>(entity)` wraps the entity in an `IResult<TDto>` that only calls
`mapper.Map<TDto>(entity)` when the caller reads `.Value` — i.e. after the pipeline's
`SaveChangesAsync()` has run and any DB-generated values (sequence-assigned IDs, defaults) are
populated on the entity. Use it for create actions; a plain `Result.Ok(mapper.Map<TDto>(entity))`
(see `Update.cs`) is fine when nothing about the DTO depends on `SaveChanges` having run yet.

## 8. Domain event and handler — `Minimal.AppServices/<Feature>/V1/Events/`

Reference: `Minimal.AppServices/CustomerProfiles/V1/Events/ProfileCreatedEventHandlers.cs`

```csharp
public sealed record ProfileCreatedEvent(Guid Id, string Name);

internal sealed class ProfileCreatedEventFromMemoryHandler : Fluents.EventsConsumers.IHandler<ProfileCreatedEvent>
{
    public Task OnHandle(ProfileCreatedEvent notification, CancellationToken cancellationToken) { ... }
}
```

- The event is a plain `sealed record`. `entity.AddEvent(...)` in the handler queues it;
  `Minimal.Infra/Services/EventPublisher.cs` (`DefaultEventPublisher` override) forwards every
  queued event onto `IMessageBus.Publish(...)` after `SaveChanges`.
- A subscriber is any class implementing `Fluents.EventsConsumers.IHandler<TEvent>` — put it in
  `AppServices` (in-process concerns, e.g. logging/cache invalidation) or `Infra`
  (`Minimal.Infra/Features/<Feature>/ExternalEvents/`, e.g. `CustomerProfileCreatedEmailNotificationHandler.cs`)
  for anything backed by an external system. No manual DI registration — both projects' assemblies
  are scanned by `AddServiceBus` in `Minimal.Infra/Extensions/ServiceBusSetup.cs`.
- Two buses exist: an in-memory child bus that is **always** wired, and an Azure Service Bus child
  bus that is only added when `ConnectionStrings:AzureBus` is non-empty. If you need a subscriber to
  run over Azure Service Bus, wire its `Produce<TEvent>`/`Consume<TEvent>` topic/subscription in
  `ServiceBusSetup.cs` the same way `ProfileCreatedEvent` → `profile-tp`/`profile-sub` is wired for
  `CustomerProfileCreatedEmailNotificationHandler`.

## 9. Endpoint — `Minimal.Api/ApiEndpoints/<Feature>V1Endpoint.cs`

Reference: `Minimal.Api/ApiEndpoints/CustomerProfileV1Endpoint.cs`

```csharp
internal sealed class CustomerProfileV1Endpoint : IEndpointConfig
{
    public int Version => 1;
    public string GroupEndpoint => "/customer-profiles";

    public void Map(RouteGroupBuilder group)
    {
        group.MapGetList<CustomerProfile, CustomerProfileDto>("/");
        group.MapGetById<CustomerProfile, CustomerProfileDto>("{id:guid}");
        group.MapPost<CreateProfileRequest, CustomerProfileDto>("/").RequiredIdempotentKey();
        group.MapPut<UpdateProfileRequest, CustomerProfileDto>("/");
        group.MapDelete<DeleteProfileRequest>("/");
    }
}
```

- `IEndpointConfig` and the `MapGetList`/`MapGetById`/`MapPost`/`MapPut`/`MapDelete` fluent helpers
  come from the `DKNet.AspCore.Extensions` NuGet package, not this repo.
- **No manual registration list exists anywhere.** Every non-abstract class implementing
  `IEndpointConfig` in the API assembly is discovered and mapped by `UseEndpointConfigs` (called
  once from `Program.cs`) — adding the class is the whole registration step.
- Route becomes `/v{Version}{GroupEndpoint}` when API versioning is enabled (the default) — e.g.
  `/v1/customer-profiles`, not `/api/v1/customer-profiles`.
- `MapPost` returns `201 Created` automatically when the command type name contains `"Create"`,
  otherwise `200 OK`. It does **not** add idempotency by itself — call `.RequiredIdempotentKey()`
  explicitly on any POST that must be idempotent; callers then must send an
  `X-Idempotency-Key: {Guid}` header.
- `[FromClaim]` population on request properties (see §4) is wired per endpoint group
  automatically — no extra call needed on the `Map` method itself.

## 10. Unit / integration tests — `Minimal.App.Tests/Integration/<Feature>/V1/`

Reference: `Minimal.App.Tests/Integration/Profiles/V1/CustomerProfileActionsIntegrationTests.cs`

```csharp
public sealed class CustomerProfileActionsIntegrationTests(ApiFixture fixture) : IClassFixture<ApiFixture>
{
    [Fact]
    public async Task CreateActionShouldResolveFromDiAndPersistProfile()
    {
        await fixture.ResetDatabaseAsync();
        using var scope = fixture.CreateScope();
        var bus = scope.ServiceProvider.GetRequiredService<IMessageBus>();
        var repository = scope.ServiceProvider.GetRequiredService<IRepositorySpec>();

        var result = await bus.Send(new CreateProfileRequest { Email = "...", Name = "...", Phone = "...", ByUser = "test" });

        result.IsSuccess.ShouldBeTrue();
        await repository.SaveChangesAsync(CancellationToken.None);
        // ...assert persisted state via a Spec
    }
}
```

- `ApiFixture` (`Minimal.App.Tests/Integration/Support/ApiFixture.cs`) boots the real host once per
  test class (`IClassFixture<ApiFixture>`) against an EF Core in-memory database, with auth,
  versioning, and Azure App Config disabled via feature overrides. Variants exist for
  auth-on (`AuthOnApiFixture`), Swagger-on, and versioning-off scenarios — add a new variant only
  if your test genuinely needs a different host configuration.
- Most tests bypass HTTP: resolve `IMessageBus`/`IRepositorySpec` from `fixture.CreateScope()`,
  `await bus.Send(request)`, assert `result.IsSuccess`/`IsFailed`, then confirm persisted state
  through a `Specification`. A couple of tests go through `fixture.CreateClient()` and a real HTTP
  call specifically to prove claim-population behavior differs from calling the bus directly —
  reach for HTTP only when that's what you're testing.
- Domain events land off the request thread (the in-memory bus runs with blocking publish
  disabled) — poll for their effect with `Eventually.IsTrueAsync(...)`
  (`Minimal.App.TestSupport/Eventually.cs`) instead of asserting immediately after `Send`.
- Shape rules — internal/sealed classes, no public entity property in a DTO, max length on every
  string, no `SqlServer` package reference, Npgsql only — are enforced separately by
  `Minimal.App.Tests/Architecture/*` (NetArchTest). A new feature that violates one of these fails
  the build, not a code review.
- Coverage target ≥80% on every class you touch; `src/coverage.runsettings` scopes collection to
  `[DKNet*]`/`[Minimal*]` and excludes `*Tests`/`bin`/`obj`/`GlobalUsings.cs` — don't put real logic
  in an excluded path.

## 11. BDD tests — `Minimal.App.BDDTests/Features/<Domain>/`

Reference: `Minimal.App.BDDTests/Features/CustomerProfiles/CreateCustomerProfile.feature` +
`Steps/CreateCustomerProfileSteps.cs`

```gherkin
Feature: Create Customer Profile
  Background:
    Given the API has no customer profiles

  Scenario: Happy path — create a new profile with valid data
    When I send a create profile request with the following data:
      | Name             | Email                  | Phone       |
      | Integration User | bdd.create@example.com | +6598765432 |
    Then the response should be successful
    And the response body should contain the profile name "Integration User"
```

```csharp
[Binding]
public sealed class CreateCustomerProfileSteps(HttpClient client, ScenarioState state, BddApiFactory factory)
{
    [When("I send a create profile request with the following data:")]
    public async Task WhenISendACreateProfileRequestWithTheFollowingData(DataTable table)
    {
        var request = new HttpRequestMessage(HttpMethod.Post, "/v1/customer-profiles") { Content = ... };
        request.Headers.Add("X-Idempotency-Key", Guid.NewGuid().ToString());
        state.Response = await client.SendAsync(request);
    }
}
```

- Add a `.feature` file under `Features/<Domain>/` and a matching `[Binding]` step class under
  `Features/<Domain>/Steps/`. Reqnroll's BoDi container injects `HttpClient`, `ScenarioState`, and
  the `BddApiFactory` into the step class constructor — no manual wiring.
- `Support/ApiHooks.cs` boots one shared `WebApplicationFactory<Program>` for the whole run
  (`[BeforeTestRun]`) and resets the database before every scenario (`[BeforeScenario(Order = 0)]`),
  so scenarios don't leak state into each other.
- Every POST needs a fresh `X-Idempotency-Key: {Guid.NewGuid()}` header per request, generated in
  the `[When]` step — reusing a key across scenarios returns the first call's cached result.
- `BddApiFactory` runs with `RequireAuthorization = false`, so `[FromClaim]` properties fall back to
  the system-account default (`SharedConsts.SystemAccount`) rather than a real claim — use the
  `@redis` / Redis-backed variant only when a scenario specifically needs a Redis-backed idempotency
  store.

```bash
dotnet build src/DKNet.Templates.sln -c Release
dotnet test src/ApiEndpoints/Minimal.App.Tests/Minimal.App.Tests.csproj --filter "FullyQualifiedName~<Feature>"
dotnet test src/ApiEndpoints/Minimal.App.BDDTests/Minimal.App.BDDTests.csproj --filter "TestCategory=<Feature>"
```
